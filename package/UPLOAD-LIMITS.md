# Upload limits — candidate 0.8.4

The component's administrator limit uses decimal MB/GB (1,000,000 / 1,000,000,000 bytes). PHP's ini K/M/G syntax is parsed into bytes using PHP's binary factors. The interface still displays ordinary decimal MB/GB, never relabels the administrator's existing limit, and includes exact byte counts in rejection messages.

On the actual admin page, UploadLimits reads ini_get from that web worker: upload_max_filesize, post_max_size, max_file_uploads, file_uploads and enable_post_data_reading. It does not infer these from CLI PHP or OpenServer template files. The page shows the component cap, PHP per-file cap and PHP whole-request cap separately. Its current per-file allowance is the minimum of applicable limits, with a conservative single-file multipart reserve deducted if the POST cap is the limiting value. Additional web-server/proxy limits cannot be discovered reliably from ini_get and may be stricter.

Before change-triggered auto-upload and again before native form submission, JavaScript checks every File.size, file count and total selected bytes plus reserved multipart overhead. It uses sizes/names/types and FormData text fields only: it does not read file content, build a giant request blob or implement an upload queue. A failure shows the limiting setting and prevents the whole selection from being submitted. The button remains usable for choosing a smaller selection. If the policy/checker cannot load, upload fails closed with a reload message.

The request estimate is a conservative upper budget, not an exact measurement of the browser-generated body. It reserves at least 65,536 bytes for form fields/boundaries and 4,096 bytes per file. UTF-8 field/name/type lengths increase the reserve when necessary; rejected near-boundary selections may physically serialize slightly smaller. The effective single-file figure uses the base reserve; actual selection metadata can lower the remaining total budget. PHP unlimited upload/post settings use zero/no cap; the component cap still applies. Disabled PHP upload/body parsing and a zero file-count cap block uploads.

The server does not trust client policy or FILES size metadata. It checks authorization/POST/CSRF, current runtime limits and uploaded-file provenance, then stats actual temporary files before publishing. Actual CONTENT_LENGTH and an aggregate budget of verified temporary files are checked before processing the batch; individual size, type and collision validation remains. Actual file bytes still pass the bounded-copy/no-overwrite pipeline. Browser preflight is convenience, not server authorization.

The upload action also exists in the URL query so PHP discarding POST fields does not lose the task. If an oversized POST reaches an authenticated Joomla application with empty POST/FILES and excessive CONTENT_LENGTH, the controller produces a clear error/recovery redirect instead of treating it as an ordinary token error. The legacy display route detects the same case. No files are processed in that diagnostic path, and unauthorized users remain denied.

PHP emits its post_max_size warning while parsing the request, before Joomla/plugin code executes. If display_errors/display_startup_errors are enabled, warning output can already prevent session startup. Likewise, an upstream 413 may never reach PHP/Joomla. The extension cannot promise to catch either pre-application failure. Proper host configuration and server logging remain required; the package does not change PHP/OpenServer config or suppress those startup errors itself. See [PHP core directives](https://www.php.net/manual/en/ini.core.php) and [PHP's multipart parser](https://github.com/php/php-src/blob/PHP-8.4/main/rfc1867.c).

After any PHP limit change, reload the media page to obtain the new web-worker policy. Site-specific CGI/FastCGI overrides may be cached: PHP documents .user.ini processing and its default 300-second refresh interval [here](https://www.php.net/manual/en/configuration.file.per-user.php). The actual worker values must be re-read through Joomla before a larger upload is accepted as tested.

Unit tests cover individual and aggregate limits, 213,578,537 bytes against a 160M POST cap, multiple files, actual disk size rather than forged client metadata, discarded POST recovery, ACL/CSRF and legacy routing. These are fixtures/mocks, not proof of a successful large multipart upload on hosting. Real acceptance and any configuration changes remain separate approved steps.
